# AI本地代理 × SUB2 增强映射

## 目标

以 `AI本地代理` 为主系统，保留其代理网关、路由、协议兼容、缓存、观测与运行时编排能力；对 `SUB2` 已成熟的平台能力按官方风格做增强接入，避免重复自研。

## 一、AI本地代理 继续作为核心的能力

这些能力属于本系统差异化核心，不应被 SUB2 平台逻辑替代：

- 上游路由池、优先级、随机轮换、亲和、冷却、失败重试
- 多协议兼容与请求归一化
- 模型映射、线路模型支持、能力探测
- 流式/非流式请求转发
- 请求运行日志、活跃请求、最近请求、线路归因
- 本地缓存、上游缓存观测、异常成功体兜底
- 代理鉴权、托管 Key、线路 Key、运行配置落盘

## 二、SUB2 已成熟、应优先吸收的能力

这些能力在 SUB2 中已有更成熟的模块边界和后台/后台管理模式，不应继续在 `AI本地代理` 中做轻量平铺式自实现：

- 用户管理
- 分组管理
- 订阅计划管理
- 用户订阅生命周期管理
- 支付渠道管理
- 支付订单与支付回调管理
- 后台列表页、筛选、分页、动作菜单、密集表格布局
- 后端按域拆分的 handler / service / repo 风格

## 三、迁移策略

### A. 直接保留 AI本地代理 现有实现

- `local_proxy.runtime.*`
- `local_proxy.upstream.*`
- `local_proxy.http.*`
- `request_history` / `request_cache` / `tool_result_cache`
- 代理侧日志、线路选择、缓存观测、异常兜底逻辑

### B. 借用 SUB2 结构，不直接照抄代码

适合用来改造 `AI本地代理` 现有 Python 后端与 React 前端组织：

- 后端按域拆分，而不是继续把管理能力堆在 `server.py` / `admin/service.py`
- 列表页统一成“筛选 + 表格 + 分页 + 动作”的稠密后台布局
- 管理模块区分平台域能力与代理运行域能力
- 后台状态与统计以真实业务字段驱动，不做前端猜测

### C. 直接迁移 / 对齐 SUB2 能力模型

这些部分后续应逐步向 SUB2 的成熟能力模型对齐：

- 用户状态、角色、余额、额度、授权范围
- 分组策略、分组绑定与批量管理
- 订阅计划与订阅实例拆分
- 支付渠道配置、支付订单状态机、回调幂等处理
- 管理后台 API 分层和批量操作接口

## 四、当前差距判断

`AI本地代理` 当前已具备：

- 基础的用户 / 分组 / 订阅 / 支付渠道 / 支付订单数据表
- 基础管理 API
- 基础后台页面

但当前问题在于：

- 后端管理逻辑仍然偏轻，很多是聚合展示，不是完整平台域模型
- `local_proxy/admin/service.py` 过于集中，难以继续演进
- `server.py` 过大，管理域与代理域耦合太深
- 前端后台页已开始靠近 SUB2 稠密布局，但业务能力仍未补齐

## 五、执行顺序

### 第一波：结构治理

- 拆分 `local_proxy.admin.service` 为按域模块
- 给后续用户/分组/订阅/支付增强留清晰扩展点
- 保持现有 API 路径与前端调用兼容

### 第二波：平台域增强

- 先增强用户、分组、订阅、支付这四个域的后端模型
- 对齐 SUB2 在批量操作、状态字段、生命周期字段上的成熟做法

### 第三波：前端后台增强

- 以 SUB2 风格补全管理能力，而不是只做视觉接近
- 将代理运行域页面与平台域页面做更清晰分层

## 六、明确不做的事

- 不把整个系统迁移成“SUB2 为底座、代理只是插件”
- 不重复自研 SUB2 已成熟的用户/支付平台能力
- 不在没有模块边界的前提下继续往 `server.py` 和单一 service 文件里堆逻辑
